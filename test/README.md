# MAD test coverage

The original `MADToken.t.sol` is retained. The additional suites exercise the
accepted token and its vendored ERC-20/permit implementation without changing
production contracts or configuration.

| Suite | Additional coverage |
| --- | --- |
| `MADToken.properties.t.sol` | Contract deployer versus transaction origin; zero, one wei, full supply and maximum integer inputs; self-transfers; approval replacement/revocation; rollback of failed delegated transfers; burn/allowance interaction; transfer round trips and split-burn equivalence. |
| `MADToken.permit.t.sol` | Independently computed EIP-712 domain; deadline equality and expiry; field tampering; wrong token/chain; future and replayed nonces; shared nonces across spenders; malformed and high-s signatures; failed-permit rollback; infinite approval and signed revocation. |
| `MADToken.invariant.t.sol` | Four actors executing transfers, approvals, delegated transfers, burns, permits, rejected spends/signatures and privileged-call attempts in random order. |

The supplied conservation, state-transition, round-trip, adversarial and
token-specific discovery guides were applied to this implementation. The retained
properties have concrete bases:

| Review pass | Property and basis | Executable check |
| --- | --- | --- |
| Conservation | The constructor mints exactly `1_000_000_000 * 10**18` (`src/MADToken.sol:38`); only holder burns reduce supply (`src/MADToken.sol:47`). All balances must sum to live supply, and live supply plus successful burns must equal the original mint. | `invariant_supplyEqualsBalancesAndOnlyBurnsReduceIt` |
| State transitions | Transfers debit and credit exactly the requested amount; approvals replace allowances; finite delegated spends consume allowance; successful permits alone increment nonces. Sources: vendored `ERC20.sol:99,120,142,176,294` and `ERC20Permit.sol:42`. | Balance, allowance and nonce ghost invariants; failed-call rollback tests. |
| Round trips | With exact transfers and no conversion or fee, a transfer followed by its reverse restores balances. Two positive burns have the same result as their sum. | `testFuzz_transferRoundTripRestoresBalances`, `testFuzz_splittingBurnsHasTheSameEffectAsOneBurn` |
| Adversarial sequences | A spender cannot exceed its authorization; a failed spend or permit cannot consume authorization; a signature cannot authorize another message, token, chain or nonce. Remaining holders must still be able to move all their tokens. | Rejection handlers, permit suite, and `afterInvariant` consolidation. |
| Token-specific behavior | Self-transfers conserve balances, zero transfers are valid for nonzero addresses, burns never credit address zero, and infinite approval persists until explicitly replaced. Sources: vendored `ERC20.sol:156,176,294` and the MAD burn function. | Boundary tests, handlers and conservation invariant. |

The invariant model uses a closed set of four holders, including the actual
deploying contract. Initial funding uses real token transfers. Ghost balances,
allowances, nonces and cumulative burns start from the specified mint and are
updated from authorized inputs, not copied from token getters. The token is never
called directly by the invariant fuzzer: an explicit selector list targets only
the handler. Rejection handlers check specific errors and leave the model
unchanged, so any partial state mutation is detected by the same invariants.

Inline settings request 256 invariant runs of depth 128 with
`fail-on-revert = true`. Zero, one wei, full balances and maximum allowances are
deliberately sampled alongside other amounts. Expected token reverts are asserted
inside the handler; unexpected handler reverts fail the campaign. A deterministic
mixed-sequence test also exercises successful spending, burning, permits,
rejections and complete depletion. Each random sequence ends with a check that
every holder can transfer its full remaining balance.

The two new stateless fuzz suites request 1,000 runs per property. Tests are
self-contained, need no RPC or additional dependencies, and never read or change
environment variables from Solidity. Test identities and signing keys are local
fixtures generated by forge-std.

Run with the assignment's seed (the output/cache overrides keep generated files
in disposable scratch space):

```sh
FOUNDRY_OUT=test/scratch/out FOUNDRY_CACHE_PATH=test/scratch/cache forge build
FOUNDRY_OUT=test/scratch/out FOUNDRY_CACHE_PATH=test/scratch/cache FOUNDRY_FUZZ_SEED=0x393c41d7b57a2cb4d2518dbde7350e99aa32cb47580b9925b13775956eebe319 forge test
```

The supplied protected launch checks were reviewed as input. This repository does
not contain their factory/Uniswap harness or launch parameters, so these additions
exercise the local token rather than claiming a live pool or fork integration run.
